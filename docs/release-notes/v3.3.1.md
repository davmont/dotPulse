# dotPulse 3.3.1 Release Notes

**Release date:** 2026-11-21

dotPulse 3.3.1 is a **security release**. Any user whose *User Type* was "Administrator", whatever their roles, could set a new password for any account and take over the site; every user created by an LDAP login had that type. A permission rule on a company or department could also grant edit and delete rights on a project's tasks. **Upgrade every installation of 3.3.0 or earlier**, first of all sites that use LDAP login. See advisories [GHSA-f4p7-xmx4-p546](https://github.com/davmont/dotPulse/security/advisories/GHSA-f4p7-xmx4-p546) and [GHSA-v99x-f92v-39qf](https://github.com/davmont/dotPulse/security/advisories/GHSA-v99x-f92v-39qf).

It upgrades 3.3.0 in place, with no database changes.

---

## Security

- **Password change by user type** (high). The **change password** window did not ask for the current password when your *User Type* was "Administrator", and never checked that you may edit the user whose password you set. The user type is only a label (CEO, Manager, Administrator...) and gives no rights, so a read-only guest of that type could set the `admin` password and log in as `admin`. Users created at their first LDAP login got the type, so on LDAP sites every such user could. Now another user's password needs the rights of the user form (edit users); your own needs your current password. Users created by an LDAP login get the type *Default User*.
- **Task rights from unrelated rules** (medium). A user allowed to edit a project may work on its tasks, but the check took any of the user's permission rules whose item had the project's id: a rule on a company or department with that id, or even a deny, gave edit and delete rights on the project's tasks. Now only the user's deciding rule on that project counts, and only if it allows editing.

## Fixes

- **Passwords are kept as typed.** A password with `'`, `\` or a space at either end was stored as another one when set in the user form or the change password window, so its user could not log in with it. Users this happened to can now set it again, or use the forgotten-password link.
- **Changing your own password in the change password window** always said the old password was wrong.
- The **minimum password length** (System Admin › Security and sessions) is checked by the server, in the user form and the change password window, not only in the browser.

## Upgrading

1. **Back up** the database and the `files/` directory.
2. **Replace the code.** Keep `includes/config.php` and `files/`.
3. **Run the installer** (`install/` in a browser) to record the new version. There are no database changes. Then remove `install/` again or deny access to it.
4. **Check the audit log** (System Admin › Audit log, event `password.changed`) for password changes you don't expect, and set the *User Type* of users who are not administrators to another value: it is only a label, but some add-on modules still read it.

From a version older than 3.3.0, read [the 3.3.0 release notes](v3.3.0.md) first.
